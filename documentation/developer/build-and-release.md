# Build & Release

There is no build or compile step — Hole ships as a set of bash scripts and config files.

## Runtime requirements

- **docker** or **podman**, with a working `compose` plugin (`detect_container_runtime` checks
  both; `HOLE_RUNTIME` env var forces one)
- **jq** — settings merging and all JSON parsing
- **jv** ([santhosh-tekuri/jsonschema](https://github.com/santhosh-tekuri/jsonschema)) —
  settings validation
- **sha1sum** — project name hashing
- **curl** or **wget** — update checks, installer
- **flock** — optional; serializes DinD cache syncs (skipped with a warning if absent)

Supported platforms: Linux and macOS (enforced by `install.sh`).

## Installation layout

`install.sh` (runnable standalone, `curl | bash`):

1. Resolves the latest GitHub release of `lukashornych/hole` via the API
2. Downloads and extracts `hole.tar.gz` into `~/.local/share/hole/`
3. Creates a wrapper at `~/.local/bin/hole` that execs `~/.local/share/hole/hole.sh`

The tarball contains a `version` file (generated by the release workflow). Its presence is what
distinguishes an installed copy from a dev checkout: `check_for_update` and `cmd_update` are
no-ops without it.

## Update & uninstall

- `hole version` / every `hole start` silently checks the GitHub API (1s timeout) and prints a
  notice when a newer release exists.
- `hole update` (`cmd_update`): compares semver, then `exec`s a temp wrapper script that runs a
  temp copy of `uninstall.sh --soft-wipe` followed by `curl install.sh | bash`. The temp-copy +
  `exec` dance exists so the running script can safely delete its own install directory.
  `--soft-wipe` preserves the DinD cache volumes (and legacy agent-home volumes) while removing
  containers, images, networks and hole files.
- `hole uninstall` (`cmd_uninstall`): same temp-copy trick, full wipe — removes install dir,
  wrapper, and **all** `hole-sandbox-*` Docker resources including volumes.

## Release workflow (`.github/workflows/release.yml`)

Triggered on every push to `main` (i.e. merging `dev` → `main` releases):

1. **Version resolution** — `codacy/git-version` with `v` prefix; commits matching
   `feat(...):`/`feat:` bump the **minor** version, everything else bumps the patch. This is why
   [conventional commits](guidelines.md#git-workflow) are mandatory.
2. **Version file** — the resolved version (without `v`) is written to `version` and packaged.
3. **Packaging** — an explicit `cp` list assembles the `hole/` directory and creates
   `hole.tar.gz`. **New source files must be added to this list** or they will be missing from
   installations ([recipe](recipes.md#add-a-new-source-file)). Developer documentation, CI
   config, and `install.sh` itself are intentionally not packaged (`install.sh` is fetched from
   the repo `main` branch).
4. **Publishing** — `release-drafter` creates and publishes the GitHub release (notes template
   in `.github/release-drafter.yml`, labels drive the changelog categories), and `hole.tar.gz`
   is uploaded as a release asset.
